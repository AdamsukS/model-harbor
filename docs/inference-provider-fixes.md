## 已修复

- 原生路由器声明 keep-alive，但立即复用其连接可复现 ECONNRESET。
  实测默认 Node Agent 连续三次为 200/reset/200；关闭上游连接复用后三次均 200。
  网关每次使用新的 loopback 连接，无自动重放 POST。
- 实际模板与 tokenizer 预检查总预算，超额明确报 CONTEXT_LENGTH_EXCEEDED。
- Schema 白名单与 Ajv 完整结果校验，拒绝底层不能强制的约束；覆盖流式与非流式。
- SSE 排队及等待首包期间每 15 秒心跳；迟到错误有结构化 error。
- 机器可读错误码、Request ID、失败阶段、重试建议、未知用量为 null、本服务不计费。
- /v1/models 附加实际服务限额；明确幂等未支持，拒绝被误认为已生效的幂等键。
- 网关 SIGTERM 等待在途请求；launchd 的实际退出宽限需以运行状态核验，见文末修正。
  强制终止、模型 worker 重启和单实例维护仍不能保证零中断。
- 部署改用包含 Schema 验证依赖的单文件 bundle，避免 macOS launchd 读取 Downloads 依赖失败。

## 610 秒公网超时的已确认根因与修复

2026-09-08 12:25:45 UTC，管理员连接核查确认：

- 宿主机 Caddyfile 已是 1810s，但容器中的单文件 bind mount 内容与宿主机不同。
- Caddy admin API 返回的实际运行配置仍是 610000000000 ns，即610秒。
- Caddy 错误日志明确为 `net/http: timeout awaiting response headers`，对应 HTTP 504，耗时610.00秒。

因此这次610秒故障来自我们部署的公网反向代理，不能归因于最终用户客户端。
宿主机更新文件后，容器的单文件挂载仍指向旧 inode，使普通容器内文件重载继续读取旧值。

修复时先将宿主机文件通过 stdin 交给容器中的 Caddy adapt/validate，比较其完整配置与运行配置，
确认唯一差异是该 API 站点的 response_header_timeout 从610秒增为1810秒。
保留旧运行配置和宿主机配置备份后，再通过 stdin 热重载，并从 admin API 确认运行配置完全匹配。
容器 PID 未改变，没有重启容器。本机网关仍使用1800秒总请求期限。

新增 `scripts/reload-inference-proxy.sh`：从宿主机创建私有配置快照，校验通过才加载同一快照，
避免读取旧 bind mount 或在验证与重载之间读到不同文件。两个回归用例和类型检查通过。
新脚本不会重启容器；若之后重建容器，Docker会重新绑定当前宿主机文件。

旧配置已经接收的请求可能继续沿用610秒期限；验收必须使用热重载后新发起的请求。
已于12:26:16 UTC发起直连公网的新非流式长请求，等待完整结果后再报告端到端验收。

修复前建立的直连公网对照请求已完成：610.238秒返回504，与 Caddy 的旧610秒运行配置一致。

## 原生路由取消泄漏：复现与修复

热重载后公网对照在1800.342秒返回504 / REQUEST_TIMEOUT，已越过610秒，
但未通过端到端成功验收。本机同体请求在1553.946秒返回200，8192输出 tokens、length。
原生槽位日志显示，部分网关已记录断连的请求仍生成数十分钟；已取消的排队请求还会开始运行。
这些遗留任务会占据槽位，使后来的请求在队列里耗尽1800秒总期限。

固定源码 `server_http_proxy` 的析构只关闭消息 pipe，没有关闭阻塞中的上游 HTTP 请求。
`patches/llama-router-cancel.patch` 复用 cpp-httplib 线程安全的 `ClientImpl::stop()`，
在关闭 pipe 后中断对应上游 socket，使模型进程能感知断连并取消任务。
`python3 scripts/test-native-proxy-cancel.py /path/to/build` 链接实际静态库，
分别覆盖等待响应头及等待正文：原版两项均未在1秒内关闭连接，补丁后两项均通过。
Release原生构建成功；测试保持进程存活，避免把进程退出时的关闭误认为取消成功。

13:00:41 UTC开始临时对公网新的推理POST返回429 SERVICE_MAINTENANCE、Retry-After:60，
保留现有请求，等待它们结束后安装修复。安装后仍需真实模型的取消、正常生成和公网长请求验证。
24小时验收尚未恢复，不能报告全部通过。

真实模型回归进一步复现：持续查询槽位等其他任务通知会让
`server_response::recv_with_timeout` 的相对等待重新计时，导致取消检查饥饿。
补丁增加固定的 steady_clock 截止时间，以 `wait_until` 等待，不因无关通知延长。
对应静态库回归持续产生其他任务通知，原版1秒期限实际耗时4.099秒，测试失败。

launchd 运行核验还发现：plist写入 ExitTimeOut=1810 后，当前 macOS 的实际退出期限仍为60秒。
生成器现将该值限制为60秒；不能把它描述为支持30分钟无中断退出。
本次采用入口维护、等待网关在途归零后再重启的流程，避免依赖该宽限强行排空长请求。
